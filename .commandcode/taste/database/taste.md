# Database

- Prefers adding new columns to the database schema to store new data fields (e.g., tension factor, hypertension reason) rather than using workarounds. Confidence: 0.65
- Tracks the database schema closely; expects data already present in the DB to appear in the UI, and treats missing display of existing DB data as a bug to diagnose. Confidence: 0.6
- Keeps multiple years of the same dataset (e.g., 2025 and 2026 KR reports) in the same table, distinguished by date, syncing from per-year Google Sheets that share identical column structure (the KR sync loops both `Loading& Unloading 2025` and `Loading& Unloading 2026` into `kr_reports`), rather than splitting into separate tables per year. Confidence: 0.65
- For Google Sheets → Supabase sync scripts, uses delete-then-insert (never per-row update/upsert) plus batched inserts (200 rows per request, with `Prefer: resolution=merge-duplicates` on the insert) to stay within Apps Script execution time limits; the "send data" scripts delete rows for a scope before re-inserting — per area for trips/leadtimes (`?area=eq.<area>`, i.e., delete_then_insert with `match: { area }`), per date for kr_reports, and for the out-of-town (luar kota) leadtimes sheets and the tenko health-check sync a combined IN filter over tanggal+area (`tanggal=in.(...)&area=in.(...)`, dates chunked ~30-50 per delete request) — not a whole-table replace; the spreadsheet remains the source of truth. Because of that variant, the sync endpoint's `match` filter must accept array values (→ IN filter) as well as single eq values. Confidence: 0.85
- Anxious about the AI accidentally deleting/modifying the production Supabase database ("gw ngeri ai ngapus database gw"); expects the agent to keep DB access read-only (SELECT via anon key only), to proactively explain the safety boundaries that protect the data (RLS policies, anon vs service_role keys, daily backups, not committing .env), and to actively verify those protections when asked to check ("oke coba cek ya") — auditing .env gitignore, absence of service_role keys in code, auth-gated write paths, and probing whether RLS actually rejects anon writes — rather than just offering reassurance. Confidence: 0.85
- Explicitly wants Row Level Security enabled on all database tables with a consistent policy model: anon (public) gets SELECT/read-only access only, while INSERT/UPDATE/DELETE are restricted to authenticated users — stated directly ("aktifkan rls, tapi bisa di select untuk anon bisa dibaca gitu, tapi ga bisa insert update delete") and expects the agent to produce runnable SQL policies implementing exactly that. Confidence: 0.8
- Security-conscious about API secrets: worried that the service_role key embedded in a Google Apps Script could be exposed to anyone who can view the script ("gw ngeri bisa dibuka orang nih"); prefers secrets to live server-side only — a Supabase Edge Function called with a random secret header (explicitly chose this approach when offered: "kita coba opsi 1") over a dedicated auth user, plus rotating/regenerating the service_role key after migrating the pipeline — instead of keeping privileged keys in client-visible code. Confidence: 0.92
- For read-only lookups in client code (e.g., fetching the drivers name→id map in Apps Script), prefers using the public anon key with RLS restricting it to SELECT — anon key is safe for reads — while keeping write operations (delete/insert) behind the server-side secret, so no service_role ever appears client-side. Confidence: 0.8
- All tables except `eco_driving` are fed from Google Sheets via Apps Script into Supabase; expects RLS/security changes to account for that pipeline (service_role bypasses RLS, so policies can go live without breaking the sync) and to warn about external writers that would break once anon writes are blocked. Confidence: 0.7
- The tenko (driver health-check) sync follows the same delete_then_insert pattern over `tanggal+area` IN filters; the script uses per-area `FILE_CONFIGS` (spreadsheet id + sheet name + column-index mapping), a dedup guard keyed on `tanggal+driver+sis+dia`, defensive parsing with fallback defaults (denyut_nadi 80, suhu 36.5, oxygen 98, rest 8), and a payload merged across all areas sent in one call. Confidence: 0.6
- Project stays on SQL (Supabase/Postgres) rather than NoSQL: heavy range/aggregation queries (Route Analytics, leadtime per bulan) and strict typing are needed, even though the flexible/varying `checkpoints` structure would suit NoSQL documents; migrating existing service layers (dataFetcher, ecoDataFetcher, tenkoService) from SQL to Firestore is deemed too large a rewrite — after weighing the SQL vs NoSQL trade-offs the user explicitly settled on SQL ("njir enakan sql ah"). Confidence: 0.8
