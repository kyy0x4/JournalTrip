- Verifies behavior by refreshing the page in the browser; data that doesn't persist across refresh is treated as a real bug (save-to-DB issue) to fix. Confidence: 0.6
- Expects the agent to first explore and understand the project structure/codebase (config files, folders, data layer, routing) before working on tasks. Confidence: 0.5

- When updating scripts that process per-year Google Sheets, wants the update to keep covering all existing sheets/years (e.g., sync 2025 and 2026 in one run via a loop) rather than swapping a single constant and silently dropping coverage of the other sheet. Confidence: 0.6
- Uses GitHub as the remote for the project; issues short commands like "oke push" / "oke push ke github" / "oke gas push" and expects the agent to run the full git workflow (status check, staged commit with clear message, push) end-to-end without further instruction. Confidence: 0.8
- Approves/triggers offered actions with terse informal commands ("gas update", "oke push", "gas pull", "coba dong bantu deploy", "lanjut semua" to green-light finishing all remaining audit items in one batch, picking among proposed options with "kita coba opsi 1,") and expects the agent to just execute the change immediately — including running the full multi-step deployment (CLI check, project link, secrets, deploy, live tests, cleanup) — without asking for further confirmation. Confidence: 0.85
- When a displayed metric, chart, or UI behavior looks wrong (e.g., a trip duration, a valley in a trend line, a shift toggle that rejects Night and snaps back to Day), asks the agent to double-check ("coba di cek" / "masih ada lembah... coba cek") and expects root-cause investigation — verifying against actual source data, the underlying library behavior, or by reproducing in the browser — before fixing, plus re-verification that the reported symptom is truly gone afterward, following up again if the issue persists (e.g., after an avatar fix, reports back "foto nya masih huruf gitu" to say the symptom remains). Confidence: 0.8
- Treats the original source Google Sheet as ground truth for analytics data; when a computed metric contradicts the sheet (e.g., segment C Bakauheni→destination showing 7 minutes for a trip that actually spanned multiple days — "di sheet itu aslinya beda hari loh"), expects the agent to fix the calculation so it reconstructs the real absolute timeline (cross-midnight/multi-day from bare "HH:MM" checkpoints) and matches the sheet, rather than patching the displayed number. Confidence: 0.7
- When a fix/experiment turns out unsatisfying, prefers abandoning it and reverting the working-tree changes back to the original state via git (e.g., "gajadi dah balikin kaya awal aja") rather than continuing to iterate; already-committed/pushed work is kept untouched. Confidence: 0.7
- Checks behavior on the live/deployed site as well as locally; when a bug reproduces only on live and not on the local build, treats it as a sign the deployed version is stale/out of sync with the repo and pulls the latest code to verify (e.g., "gw cek di live nya ngebug makanya gw coba pull") — expects the agent to compare local/repo state against the deployed version and check deploy config/URL when diagnosing. Confidence: 0.65
- When a reported bug appears in a screenshot but the fix is already present in local code, prefers diagnosing why the screenshot is stale (old build, cached page, unrefreshed HMR) over re-applying the fix; communicates the expected fix to the user and instructs them to hard-refresh (e.g., Cmd+Shift+R) before re-checking. Confidence: 0.6
- Wants local backup/scratch directories (e.g., `.commandcode.bak/`) kept out of commits; agent stages only source and config changes, and confirms the backup was excluded. Confidence: 0.7
- Wants commit messages written in Indonesian with a `fix:` (or similar) conventional-commit prefix and `Co-authored-by: CommandCodeBot <noreply@commandcode.ai>` trailer. Confidence: 0.7
- Prefers applying the security lockdown (RLS policies) right away and dealing with the affected external pipeline (e.g., migrating Apps Script off service_role) as a follow-up, rather than blocking the DB hardening on completing the pipeline refactor first ("gw mau jalanin rls policies dlu nih"). Confidence: 0.7
- The Apps Script → Supabase sync scripts ("send data") delete existing rows for a scope first, then re-insert the latest spreadsheet data — NOT incremental insert/update of new rows. The actual production code deletes per area (`?area=eq.<area>` on trips/leadtimes) then re-inserts all rows for that area, so any replacement (e.g., the sheet-sync edge function) must support delete_then_insert with a match filter (e.g., `{ area }`), and the match must also accept array values (→ IN filter) because the out-of-town leadtimes sync deletes by `tanggal=in.(...)&area=in.(...)`; the spreadsheet stays the source of truth. Confidence: 0.85
- After the agent deploys/sets up an integration, prefers to run the manual end-to-end test himself (e.g., "gw coba nih ya," before testing the Apps Script sync) using a concise quick-start guide, then reports back results/errors (e.g., pasting the exact sync failure message) rather than having the agent perform the final client-side test. Confidence: 0.7
- When the agent provides an example/migration file for the user to copy into their own project (e.g., an Apps Script replacement), it must be complete and runnable standalone: every referenced helper function implemented in full, no placeholder comments like "TETAP SAMA seperti sebelumnya" that skip real code — the user applies the file verbatim, so a missing function surfaces immediately as a runtime error (e.g., "ReferenceError: getColumnConfig is not defined"); the agent should also grep the delivered file to confirm no unwanted leftovers (e.g., old service_role key references) before handing it over. Confidence: 0.7
- When a fix requires a manual step only available in the dashboard (e.g., running the RLS SQL in the Supabase SQL Editor), the user executes that step himself and confirms completion tersely ("oke gw udah jalanin sql leadtimes nih, kita lanjut selanjutnya"), expecting the agent to verify the result server-side (e.g., via CLI RLS/policy checks), fix any remaining root cause, and proceed straight to the next item — not re-run or re-explain the manual step.
